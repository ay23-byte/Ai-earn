# Initial threat model

This table is the Phase 0 planning baseline, not a claim that all mitigations are implemented. At that point there was no application or production deployment. Likelihood is preliminary and depends on the eventual design; impact is potential impact if the feature is introduced. See the Phase 2 interim notes below for the limited controls since added. All tests and recovery procedures must be implemented or exercised in the relevant phase.

| Threat / asset | Likelihood / impact | Planned prevention and detection | Recovery and verification needed |
|---|---|---|---|
| Account takeover, stolen credentials / accounts | Unknown / high | Secure authentication, session expiry, rate limits, secret isolation and sensitive-action audit; monitor suspicious sign-ins | Revoke sessions and rotate credentials; test auth, expiry and rate limiting (Phase 2) |
| Cross-user access or leakage / customer data | Unknown / high | Deny by default; server-side ownership checks, redacted logs; monitor access audit | Contain access, assess exposure; test cross-account access and log redaction (Phases 1–2) |
| Prompt injection and malicious tool arguments / authority and secrets | Unknown / high | Treat source text as data; independent policy, schema validation, least privilege and review; record suspicious attempts | Stop automation, preserve evidence; test untrusted instructions and unauthorized tool calls (Phases 5, 13) |
| Malicious uploads or code / host and files | Unknown / high | Bounded size/type validation, no arbitrary execution, isolation and resource limits; record rejected uploads | Quarantine and restore; test traversal, malformed and resource-exhausting files (when uploads are added) |
| Fake jobs, clients and payment evidence / money and personal data | Unknown / high | Manual evidence review, risk flags; separate unverified, confirmed and settled states | Stop contact, preserve records, reconcile; test deceptive listings and financial states (Phases 4, 9–11) |
| Forged, replayed or out-of-order webhooks / ledger | Unknown / high | Verify provider signatures server-side; idempotent event processing and reconciliation; alert mismatches | Disable integration, preserve event records, reconcile; test invalid signatures, duplicates and ordering (Phase 10) |
| Fraudulent refunds or chargebacks / money | Unknown / high | Human approval, provider validation and audit; monitor disputes | Freeze action and reconcile; test refund and dispute paths (Phases 9–11) |
| Dependency compromise, malicious browser extensions or tools / secrets and execution | Unknown / high | Minimize and lock dependencies, audit updates; avoid exposing credentials to untrusted tools | Revoke credentials, restore known-good versions; inspect dependency and permissions changes (Phases 1, 15) |
| SSRF, unauthorized outbound traffic or API cost exhaustion / network and budget | Unknown / high | Restrict destinations, redirects and internal IPs; timeouts, bounded responses, quotas and hard spending controls; alert thresholds | Disable integration, review logs and costs; test blocked addresses and limits (Phases 12–13) |
| Accidental deletion, database corruption or bad migrations / records | Unknown / high | Transactions, constraints, backups and migration plan; monitor failed writes | Restore verified backup and reconcile; rehearse restore and interrupted operations (Phase 3 onward) |
| Misconfigured deployment or automation privilege abuse / all assets | Unknown / high | No public deployment until hardened; scoped approvals, emergency stop and auditable actions; alert unauthorized attempts | Disable affected automation, preserve evidence, roll back; test approval boundaries and stop (Phases 13, 15) |
| Copyright, privacy or platform violations / customer rights and business | Unknown / high | Review rights, retention, consent and platform terms; manual publication approval | Stop distribution, document incident and assess obligations; review actual workflow (Phases 6–8, 12) |

For any suspected compromise, stop affected operations, preserve evidence without exposing secrets, revoke affected credentials, assess data and transaction impact, restore and reconcile as appropriate, and document and test the fix. No emergency-stop mechanism exists yet.

## Phase 2 interim: local auth

The experimental offline auth component adds salted PBKDF2 hashes, digest-only random sessions and recovery codes, persistent local throttling, fixed-event audits, ownership checks and POSIX owner/mode checks. Automated tests cover these controls, not their resistance to a compromised operating-system account or hostile same-user processes. The user reports passing Windows ACL tests, but account storage is disabled on Windows pending terminal verification and security review; there is no approved Windows account workflow yet. A stale database backup can resurrect revoked sessions and old credentials; restore only to a separate protected path, revoke sessions and rotate credentials before use. See [SECURITY.md](SECURITY.md). This does not change the unimplemented status of browser protections, uploads, autonomous actions or payments.
