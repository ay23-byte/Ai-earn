## Observed baseline (Phase 0, commit 16bd10f)

The repository has no running application or architecture: only a README existed at the audited commit. There are no frontend/backend routes, authentication mechanisms, data stores, workers, APIs, payment components, integrations, or deployment configuration. Consequently there is no data flow or schema to assert as implemented.

## Target boundaries (not implemented)

- A local-first interface should display only persisted, real records and clearly identify empty or unverified states.
- Application services should validate input and enforce authorization and approval policy independently of any AI model or UI. Business rules and state transitions belong server-side, not in hidden controls.
- Durable storage, ownership, transactional state changes, idempotency and audit records must be established before workflows depend on them. Keep expected, invoiced, confirmed, settled and net income distinct.
- External sources and model output are untrusted data. Connectors should have narrowly scoped credentials, bounded requests and manual fallbacks; consequential actions require explicit policy enforcement and approval.
- Payment events must be independently verified and reconciled with the provider. No browser-provided status, screenshot or unverified webhook establishes payment.

These are requirements, not evidence of implemented controls. Actual language, framework, storage and authentication choices are deferred to the gated implementation plan. Since no project exists, a new minimal application can be justified, but a broad rewrite, public deployment and live financial operations are not justified by this audit.

## Recovery boundary

This documentation-only audit changes no application or database. Use `git diff` to review changes; restore individual audit files only after confirming they contain no user edits. Future implementation must document backups, tested restores, migration reversibility, incident containment and rollback appropriate to its actual storage and deployment.

## Phase 1 foundation (historical increment)

`python -m ai_earn status` runs a local process. `ai_earn/config.py` validates the environment, `status.py` reports only implemented capabilities, `responses.py` provides success/error envelopes, `events.py` emits only fixed structured event names, and `__main__.py` handles presentation and sanitized failures. Configuration has no secret fields, and events accept no arbitrary message, exception or context. This omission-based design does not guarantee safety of unrelated future logging; every future input and log path still requires review.

At the Phase 1 checkpoint the program did not listen on a network, call external services or write application data. Environment labels did not partition resources. Phase 2 subsequently introduced the auth-only database described below; no HTTP API existed at that checkpoint, and production was explicitly not ready. See [DECISIONS.md](DECISIONS.md) and [PHASE_STATUS.md](PHASE_STATUS.md).

## Phase 2: experimental local account component

`auth_storage.py` initializes an auth-only SQLite schema and validates a private POSIX file/directory. `auth.py` handles hashed credentials, throttling, session checks, ownership, recovery and fixed audit events; `auth_cli.py` is the terminal adapter. Access checks are in the service rather than the terminal UI. These controls are testable in-process, not an OS sandbox or a network server. Windows development authentication uses Windows ACL checks; the user reported passing no-override tests and the missing-database fix at `72241cc`. Other non-POSIX platforms and production-labelled auth are disabled. Phase 2 passed only the offline development scope with documented limitations. No browser or external API exists. For the trust boundary and backup hazards, see [SECURITY.md](SECURITY.md).

## Phase 3: separate state-storage foundation (in progress)

`state_storage.py` is internal infrastructure, separate from auth storage, with a distinct SQLite application ID and version 1 bootstrap history. It explicitly creates only new files, rejects uninitialized/unknown schemas, and uses transactions plus checked, non-overwriting SQLite backup to new files; restoration is another copy to a new path. It reuses the auth component's platform-private path checks and its write-transaction helper; changes to those private helpers require regression testing both modules. Opening storage is not authorization. There are no public interfaces or complete business workflows. The internal experimental opportunity-draft service described below independently checks session and record ownership. An explicitly confirmed, backup-first version 1-to-2 migration adds constrained audit and operation-key infrastructure tables; they do not enforce authenticated writes, append-only business audit or full idempotency. `state_authorization.py` provides an internal session-bound unit of work, locking auth before state, deriving the actor from a live session and checking expiry again before state commit. It does not itself enforce per-record ownership and has no public operations. Auth and state commits are separate, so a failure after state commit can report an ambiguous outcome; mutation services must provide durable idempotency. Callers must use a fixed trusted auth/state pairing and never hold the locks in reverse order. Only disposable data is supported. The user reported passing Windows tests for the migrations through v3, authorization and opportunity drafts. The user reported passing Windows tests for v4/v5 task plans and order drafts; the exact commit was not supplied. The user later reported Windows tests covering v6–v9; exact commit and Python version were not supplied. V10 has not been tested on Windows.

### Experimental opportunity drafts

The explicit, backup-first v2-to-v3 migration adds an `opportunity_drafts` table. `opportunity_drafts.py` provides an internal Python service to create, read and archive a user-entered title. Ownership is derived from the live session; the only supported transition is `draft -> archived`. The service commits the record, a fixed audit event and owner-scoped idempotency key together in the state database, and returns the same record ID on an identical retry. It rejects a key reused with different inputs. The audit is not tamper-evident; rejected access is not a business-audit event. Keys are retained in plaintext and must not contain secrets. The trusted caller must supply the same fixed auth/state pair every time. There is no CLI or UI for this service, no discovery or verification, and no external action. A draft is not proof of an actual opportunity, customer or income. No real data is supported.

### Experimental task plans

The explicit, backup-first v3-to-v4 migration adds `task_plans` and preserves existing v3 opportunity drafts and retry keys. `task_plans.py` offers an internal Python service for an owner to create, read and cancel a plan; the only transition is `planned -> cancelled`. A plan does not execute work, enter a task queue, validate output or become complete. The service derives the owner from a live session and commits the task record, fixed audit event and owner-scoped operation key together. It reuses the draft module's bounded input and request-digest helpers; future changes to those helpers must regression-test both services. Operation keys are shared across record types per owner. The service uses the same trusted fixed auth/state pairing, local-OS trust assumptions, audit limitations and disposable-data restriction as opportunity drafts. There is no task UI, worker or external action; the user subsequently reported passing v4 tests on Windows.

### Experimental order drafts

The explicitly confirmed, backup-first v4-to-v5 migration adds `order_drafts`, preserving prior records and retry keys. `order_drafts.py` provides internal session-owned create, read and `draft -> cancelled` operations. A draft contains a title and a proposed integer amount from 0 through 1,000,000,000,000 paise inclusive, in INR only. The service rejects booleans and floats; a canonical request digest covers the normalized title, amount and currency. Fixed audit events and operation keys commit atomically with each mutation, sharing the owner-scoped key namespace with opportunity drafts and task plans. This is only a disposable estimate, not an accepted order, contract, invoice, payment or earnings. There is no customer, external action or financial workflow. The trusted fixed auth/state pair, separate database commits, local-OS assumptions, shared helper regression requirements and audit limitations remain. The user subsequently reported passing v4/v5 tests on Windows.

### Experimental invoice drafts

The explicitly confirmed, backup-first v5-to-v6 migration adds `invoice_drafts`. The internal `InvoiceDrafts` service creates a draft only from an owned active order draft, snapshots its proposed INR amount, and permits only `draft -> cancelled`. The service checks parent and draft ownership with the live session. A composite foreign key references the order ID and owner when SQLite foreign keys are enabled, backed by a validated unique index. Service-side session and active-state checks remain necessary. Creating a draft and its audit event and shared owner-scoped operation key is atomic. An identical retry returns its original result even after the parent is cancelled; cancelling a parent does not cancel existing invoice drafts. Multiple drafts can reference one order. These are disposable local snapshots, not issued invoices, payment demands, commitments, or income, and they have no customer details or tax logic. There is no sending, payment or financial workflow. Auth/state pairing, separate commits, OS trust and audit limitations still apply; v6 has not been tested on Windows.

### Internal state audit reads

`state_audit.py` offers a bounded, ascending ID cursor read filtered by the authenticated actor, using the existing auth-then-state transaction. It returns event metadata only, not the operation key, title, amount, token or actor ID. Global IDs can reveal gaps caused by other activity and should not be exposed to untrusted callers. The local log is neither tamper-evident nor complete, and reads do not create audit events. V6 and this reader are unverified on Windows.

### Experimental durable scheduling queue

The v6-to-v7 migration is explicitly confirmed and requires a checked pre-migration backup at a new path. `TaskQueue` offers internal owner-scoped enqueue, ready, claim, retry, timeout recovery and cancel state. It stores priority, a bounded attempt limit and backoff, optional deadline, availability time, and immutable lease records. A claim increments attempts; leases expire at the earlier of their timeout and deadline. Recovery is explicit, never automatic. A failed attempt requeues after backoff, or becomes exhausted when the attempt limit is reached or the deadline prevents another attempt. Queued items past their deadline are excluded from ready results and may be cancelled, but are not automatically changed. Recovery and retries require the current lease ID, preventing stale IDs from changing a later lease. An identical claim retry returns its original lease ID even when inactive; check `get_lease` and do not assume a retried result is current. Same state mutations atomically record fixed audit events and shared per-owner idempotency keys. Ordering is priority descending, availability time, then ID, not strict FIFO. This is scheduling state only: it does not execute work, validate output, implement approval, or establish completion. It relies on a trustworthy wall clock and trusted local caller; leases alone cannot fence external effects.

### Experimental local task review

The explicit, checked-backup-first v7-to-v8 migration adds a separate `task_workflows` table. `TaskWorkflows` uses live-session ownership and atomic audit/idempotency for `planned -> in_progress -> pending_review -> completed`; review may instead reject to `in_progress`, and pre-completion states can be cancelled. Submitted output must be nonempty, bounded UTF-8 text without most control characters; only its SHA-256 digest and byte length are stored. Review requires literal `confirmed=True`, an explicit boolean decision and output whose digest and length match the submission. An identical operation-key retry returns its original result, even after later changes. This is local state only: no worker runs, and no queue entry is linked or completed. Validation is syntactic, not business or factual validation; confirmation does not establish human identity or permission to deliver externally. Hashes may reveal guessable content. This internal disposable prototype and v8 are unverified on Windows.

### Queue consistency hardening

The queue checks the requested owned record's attempt count, lease history, current lease metadata and relevant deadline relationships; `ready` checks its returned records. Backup/restore checks inspect all v7/v8 queue records on the source and destination. Inconsistencies fail closed; they are not automatically repaired. These checks do not constitute complete database validation or tamper evidence.

### Unverified payment placeholders

The explicit checked-backup-first v8-to-v9 migration adds `payment_observations`, with a composite owner/invoice foreign key and validated unique parent index. `PaymentObservations` creates a local unverified placeholder only when the session owns active order and invoice drafts, snapshotting the proposed INR amount. It offers `unverified -> flagged -> unverified` and discard from either state, with atomic audit and owner-scoped operation keys. No evidence, customer or provider identity is captured: the placeholder is not an observation of an actual payment, not a payable invoice, not a confirmed/settled payment and not revenue. Parent cancellation does not automatically change an existing placeholder; multiple placeholders may reference one invoice, and an exact retry returns the original result. The service does not initiate or verify transactions. A payment provider and independently verified event processing must be designed and reviewed separately. Use disposable data only; the user later reported passing v9 disposable tests on Windows.

### Mutation crash/restart evidence

Disposable v9 tests terminate a child with `os._exit` at controlled points before state commit and after state commit but before the read-only auth transaction exits. They check rollback or a retry using the same owner, operation key and exact request for queue claims, local reviews and unverified payment placeholders, plus one WAL recovery/backup case. Separate-process tests also coordinate same-key and different-key queue claims. These tests do not make the separate databases atomically commit together, prove power-loss behavior or validate real-data recovery.

### Checked retry-result references

Checked state backup/restore and pre-migration snapshots inspect recognized operation-result references for the schema version and require a matching owned row. The check applies to the source and copy and may refuse databases that were previously accepted; it does not migrate or repair them. Unknown resource types and absent operation records are not checked, and a reference to the wrong record with the same owner can still pass. Checked snapshots also compare recognized audit and operation counts per owner and resource, mapping queue lease results to the audited queue record. Migrations validate the post-upgrade transaction before commit, rolling back incompatible data while retaining the checked pre-migration backup. These checks add scans and grouping during backups and migrations, not every read, and are not tamper evidence or proof of correct requests, complete history, audit, or recovery. Each recognized record now also requires exactly one creation audit event, and queue lease counts must match lease-creation audit counts. This catches some missing creation pairs; selected one-way terminal transition checks are described below. Swapping same-owner results, coordinated record/history changes and unknown types can still evade detection.

### Owner-relative audit pages

`StateAudit.list_owner_events` returns live-session owner-filtered events with a 1-based owner-relative sequence instead of global IDs. It is additive: legacy `list_events` still exposes global IDs and is internal only. Sequences are positions, not durable record IDs; deletion or restoration can shift them, and large offsets may be expensive. Neither reader is a public API or a timing/metadata side-channel defense. The audit remains incomplete and is not tamper-evident.

### Proposed-amount snapshot consistency

For checked backups/restores and migration validation, invoice snapshots in v6+ must match the amount and currency of their owned order drafts; v9 unverified placeholders must match their owned invoice. This assumes the existing services' immutable proposed amounts, but not cascading cancellation. Editable parent amounts would need a version-aware redesign, because snapshots are historical. Invoice reads, cancellation and exact retries also check the requested owned invoice against its order. Placeholder reads, transitions and exact retries check the requested placeholder and its invoice/order, and new placeholders check their source invoice. These checks do not scan unrelated records or run in the order service; cancellation still does not cascade. Equal values are not proof of authenticity or financial activity.

### Cross-version recovery rehearsal

A disposable v1–v9 migration and backup/restore rehearsal exercises multiple owned record types, a WAL database, exact retries, and an active lease. It explicitly demonstrates that subsequent mutations and recovery are absent from the restored old snapshot. The separate queue and review services remain independent; completing one does not complete the other. This rehearsal is not a real-data recovery or external-effect guarantee.

### Queue/workflow association (v10)

The explicit v9-to-v10 migration requires confirmation and a checked pre-migration backup at a new path. It adds a validated workflow owner index and a one-to-one association table with composite owner foreign keys. `TaskAssociations` creates a historical association only for an owned queued item and an owned planned workflow, with atomic audit and owner-scoped idempotency. An exact retry remains valid after either parent changes; cancellation does not cascade. `TaskAssociations.inspect` reads the linked queue and workflow under one authorized transaction, returning individual states and readiness, lease and deadline observations at the sampled wall-clock time. It does not return output hashes or titles. The results can be stale immediately and cannot authorize a claim or fence external effects. The services remain independently mutable: except for the opt-in paired operations described below, an association does not synchronize state, prove a review, run work, authorize external effects or fence a worker. It is not full queue/workflow integration. No existing user file was migrated; the user later reported a Windows gate pass at `cd7f6ff` with skips.

### Owner-scoped operation-history comparison

`StateRecoveryComparison` compares two distinct trusted state files of the same supported schema for the live-session owner. It locks auth first and both state files in deterministic path order, applies existing whole-database integrity checks and streams owner-specific operation rows to report aggregate matching, current-only, candidate-only and conflicting keys; it does not return keys, hashes or record IDs. It does not modify application records, restore or merge copies. Matching results do not establish record/audit equality, freshness, authenticity, common auth/state pairing or absence of external effects. Full-database checks can be expensive and their failure can reflect another owner; write-intent locks can block writers. This is internal disposable-data tooling, not a public security boundary or real-data recovery proof.

### One-way terminal transition checks

Checked source and destination snapshots and pre/post-migration validation compare four simple terminal states against their owner/resource audit history: archived opportunities and cancelled task plans, order drafts and invoice drafts must have exactly one corresponding transition event after their creation event, while initial states must have none. Audit insertion IDs, not wall-clock times, determine order. The check adds grouped scans, can reject previously accepted files, and is not performed on every service read. It does not cover every state machine or unknown event, prove that an operation key describes its event, authenticate history, detect a consistent record/history reversion, or repair data. Future changes to these state machines must update version-aware validation and migration tests. No schema or external action was added.

### Multi-step event sequence consistency

Checked snapshots and pre/post-migration validation stream each queue (v7+), local task workflow (v8+) and unverified payment placeholder (v9+) audit history in event insertion order and replay a fixed version-aware state machine, comparing the resulting state to the stored record. Unknown or illegal events for these recognized resources fail closed. This is a whole-database scan and may block writers or reject files previously accepted; future schema or event changes must explicitly update the corresponding versioned rules and tests. It does not validate event authenticity, exact retry requests, timing or deadlines, output correctness, other types, or a complete erased cycle. It is not queue/workflow coordination, a worker fence, financial verification, repair or proof of safe recovery.

### Opt-in paired cancellation

`TaskAssociations.cancel_pair` is an internal v10 operation that cancels both linked parents in one session-authorized state transaction only when the queue item is queued and the workflow is planned. It records each parent's normal cancellation audit and operation result, plus an association event and caller-supplied retry key; a repeated exact request returns the association ID. Two opaque generated child keys occupy the same owner-scoped operation-key namespace as caller keys; collisions are checked before writes and fail closed. They are not credentials. Auth and state still commit separately, so callers must retry ambiguous results with the same key. The ordinary parent APIs remain independently mutable and do not invoke this operation; direct cancellation does not cascade. Thus this does not enforce a coordinated lifecycle, fence leases or external effects, execute tasks, establish review, or support real data. No schema migration was added.

### Opt-in paired start

`TaskAssociations.start_pair` atomically leases an owned ready queue item and moves its linked planned workflow to `in_progress`, using the same internal claim rules as the independent queue service. It writes the normal queue-lease and workflow-start audit entries in the state transaction. The caller's key identifies the queue-lease retry; a collision-checked generated child key records the workflow start. Exact retries return the original lease ID even after it expires or is recovered: callers must check current lease state, and no observation authorizes external work. Session expiry and lease expiry before commit roll back the state transaction. Existing independent APIs remain callable and can bypass both paired operations; this is not a coordinated lifecycle, execution, human review or an external-effect fence. No schema migration was added.

### Lease-aware paired submit and review

`TaskAssociations.submit_pair` and `review_pair` reuse the ordinary local workflow transitions, checking the linked queue has the supplied current, unexpired lease before a new mutation and checking expiry again before state commit. The owner-scoped retry digest binds the association, lease, output digest/size and review decision; exact retries acknowledge an earlier result even if the lease has since expired or been replaced. That acknowledgement does not grant authority to continue work. Explicit boolean review confirmation and matching output remain required. These opt-in methods cannot prevent the independent queue or workflow APIs from bypassing the check. Approval changes only the local workflow; it does not complete or release the queue, prove human review, validate output or fence external effects. Output hashes can reveal guessable content. No schema or external integration was added.

### Opt-in paired lease retry, recovery and resumption

`retry_pair` releases an unexpired current lease when the linked workflow is in progress; `recover_pair` releases an expired current lease when the workflow is in progress or pending review, preserving any pending output. Both use the same queue retry/backoff/exhaustion logic as the independent queue service. `resume_pair` can claim a ready queue item for a linked in-progress or pending-review workflow without changing the workflow. The caller's owner-scoped retry record binds the association and lease or requested duration. Exact retries acknowledge the original result even if state has changed or a returned lease is stale; they do not confer present authority. `TaskAssociations.complete_pair` requires an owned v11 association, explicit `confirmed=True`, its currently unexpired lease, matching pending-review output and an owner-scoped operation key. ### Explicit abandonment of stranded local workflows

`TaskAssociations.abandon_pair` requires `confirmed=True` and an owned v10/v11 association. It atomically cancels the workflow and removes its pending output hash and size; for an expired queued item it also cancels the queue. An already exhausted or cancelled queue retains its truthful status and history. The operation uses normal parent audit events and collision-checked child retry keys plus an association event and owner-scoped caller key; exact retries return the original association ID. Deadline and session are rechecked before commit. Auth/state commits remain separate and ambiguous outcomes must be retried exactly.

Abandonment is destructive to the stored pending output hash/size, not approval, execution, delivery or settlement. A live or expired-but-still-leased queue is refused; recover an expired lease through existing rules before considering abandonment. Completed workflows are refused, including legacy cases in which completion and queue state diverged.
