# Architecture: baseline and proposed boundaries

## Observed baseline

The repository has no running application or architecture: only a README existed at the audited commit. There are no frontend/backend routes, authentication mechanisms, data stores, workers, APIs, payment components, integrations, or deployment configuration. Consequently there is no data flow or schema to assert as implemented.

## Target boundaries (not implemented)

- A local-first interface should display only persisted, real records and clearly identify empty or unverified states.
- Application services should validate input and enforce authorization and approval policy independently of any AI model or UI. Business rules and state transitions belong server-side, not in hidden controls.
- Durable storage, ownership, transactional state changes, idempotency and audit records must be established before workflows depend on them. Keep expected, invoiced, confirmed, settled and net income distinct.
- External sources and model output are untrusted data. Connectors should have narrowly scoped credentials, bounded requests and manual fallbacks; consequential actions require explicit policy enforcement and approval.
- Payment events must be independently verified and reconciled with the provider. No browser-provided status, screenshot or unverified webhook establishes payment.

These are requirements, not evidence of implemented controls. Actual language, framework, storage and authentication choices are deferred to the gated implementation plan. Since no project exists, a new minimal application can be justified, but a broad rewrite, public deployment and live financial operations are not justified by this audit.

## Recovery boundary

This documentation-only audit changes no application or database. Use `git diff` to review changes; restore individual audit files only after confirming they contain no user edits. Future implementation must document backups, tested restores, migration reversibility, incident containment and rollback appropriate to its actual storage and deployment.

## Phase 1 foundation (historical increment)

`python -m ai_earn status` runs a local process. `ai_earn/config.py` validates the environment, `status.py` reports only implemented capabilities, `responses.py` provides success/error envelopes, `events.py` emits only fixed structured event names, and `__main__.py` handles presentation and sanitized failures. Configuration has no secret fields, and events accept no arbitrary message, exception or context. This omission-based design does not guarantee safety of unrelated future logging; every future input and log path still requires review.

At the Phase 1 checkpoint the program did not listen on a network, call external services or write application data. Environment labels did not partition resources. Phase 2 subsequently introduced the auth-only database described below; no HTTP API existed at that checkpoint, and production was explicitly not ready. See [DECISIONS.md](DECISIONS.md) and [PHASE_STATUS.md](PHASE_STATUS.md).

## Phase 2: experimental local account component

`auth_storage.py` initializes an auth-only SQLite schema and validates a private POSIX file/directory. `auth.py` handles hashed credentials, throttling, session checks, ownership, recovery and fixed audit events; `auth_cli.py` is the terminal adapter. Access checks are in the service rather than the terminal UI. These controls are testable in-process, not an OS sandbox or a network server. Windows development authentication uses Windows ACL checks; the user reported passing no-override tests and the missing-database fix at `72241cc`. Other non-POSIX platforms and production-labelled auth are disabled. Phase 2 passed only the offline development scope with documented limitations. No browser or external API exists. For the trust boundary and backup hazards, see [SECURITY.md](SECURITY.md).

## Phase 3: separate state-storage foundation (in progress)

`state_storage.py` is internal infrastructure, separate from auth storage, with a distinct SQLite application ID and version 1 bootstrap history. It explicitly creates only new files, rejects uninitialized/unknown schemas, and uses transactions plus checked, non-overwriting SQLite backup to new files; restoration is another copy to a new path. It reuses the auth component's platform-private path checks and its write-transaction helper; changes to those private helpers require regression testing both modules. Opening storage is not authorization. There are no public interfaces or complete business workflows. The internal experimental opportunity-draft service described below independently checks session and record ownership. An explicitly confirmed, backup-first version 1-to-2 migration adds constrained audit and operation-key infrastructure tables; they do not enforce authenticated writes, append-only business audit or full idempotency. `state_authorization.py` provides an internal session-bound unit of work, locking auth before state, deriving the actor from a live session and checking expiry again before state commit. It does not itself enforce per-record ownership and has no public operations. Auth and state commits are separate, so a failure after state commit can report an ambiguous outcome; mutation services must provide durable idempotency. Callers must use a fixed trusted auth/state pairing and never hold the locks in reverse order. Only disposable data is supported. The user reported passing Windows tests for the migrations through v3, authorization and opportunity drafts. The user reported passing Windows tests for v4/v5 task plans and order drafts; the exact commit was not supplied. V6, v7 and v8 remain unverified on Windows.

### Experimental opportunity drafts

The explicit, backup-first v2-to-v3 migration adds an `opportunity_drafts` table. `opportunity_drafts.py` provides an internal Python service to create, read and archive a user-entered title. Ownership is derived from the live session; the only supported transition is `draft -> archived`. The service commits the record, a fixed audit event and owner-scoped idempotency key together in the state database, and returns the same record ID on an identical retry. It rejects a key reused with different inputs. The audit is not tamper-evident; rejected access is not a business-audit event. Keys are retained in plaintext and must not contain secrets. The trusted caller must supply the same fixed auth/state pair every time. There is no CLI or UI for this service, no discovery or verification, and no external action. A draft is not proof of an actual opportunity, customer or income. No real data is supported.

### Experimental task plans

The explicit, backup-first v3-to-v4 migration adds `task_plans` and preserves existing v3 opportunity drafts and retry keys. `task_plans.py` offers an internal Python service for an owner to create, read and cancel a plan; the only transition is `planned -> cancelled`. A plan does not execute work, enter a task queue, validate output or become complete. The service derives the owner from a live session and commits the task record, fixed audit event and owner-scoped operation key together. It reuses the draft module's bounded input and request-digest helpers; future changes to those helpers must regression-test both services. Operation keys are shared across record types per owner. The service uses the same trusted fixed auth/state pairing, local-OS trust assumptions, audit limitations and disposable-data restriction as opportunity drafts. There is no task UI, worker or external action; the user subsequently reported passing v4 tests on Windows.

### Experimental order drafts

The explicitly confirmed, backup-first v4-to-v5 migration adds `order_drafts`, preserving prior records and retry keys. `order_drafts.py` provides internal session-owned create, read and `draft -> cancelled` operations. A draft contains a title and a proposed integer amount from 0 through 1,000,000,000,000 paise inclusive, in INR only. The service rejects booleans and floats; a canonical request digest covers the normalized title, amount and currency. Fixed audit events and operation keys commit atomically with each mutation, sharing the owner-scoped key namespace with opportunity drafts and task plans. This is only a disposable estimate, not an accepted order, contract, invoice, payment or earnings. There is no customer, external action or financial workflow. The trusted fixed auth/state pair, separate database commits, local-OS assumptions, shared helper regression requirements and audit limitations remain. The user subsequently reported passing v4/v5 tests on Windows.

### Experimental invoice drafts

The explicitly confirmed, backup-first v5-to-v6 migration adds `invoice_drafts`. The internal `InvoiceDrafts` service creates a draft only from an owned active order draft, snapshots its proposed INR amount, and permits only `draft -> cancelled`. The service checks parent and draft ownership with the live session. A composite foreign key references the order ID and owner when SQLite foreign keys are enabled, backed by a validated unique index. Service-side session and active-state checks remain necessary. Creating a draft and its audit event and shared owner-scoped operation key is atomic. An identical retry returns its original result even after the parent is cancelled; cancelling a parent does not cancel existing invoice drafts. Multiple drafts can reference one order. These are disposable local snapshots, not issued invoices, payment demands, commitments, or income, and they have no customer details or tax logic. There is no sending, payment or financial workflow. Auth/state pairing, separate commits, OS trust and audit limitations still apply; v6 has not been tested on Windows.

### Internal state audit reads

`state_audit.py` offers a bounded, ascending ID cursor read filtered by the authenticated actor, using the existing auth-then-state transaction. It returns event metadata only, not the operation key, title, amount, token or actor ID. Global IDs can reveal gaps caused by other activity and should not be exposed to untrusted callers. The local log is neither tamper-evident nor complete, and reads do not create audit events. V6 and this reader are unverified on Windows.

### Experimental durable scheduling queue

The v6-to-v7 migration is explicitly confirmed and requires a checked pre-migration backup at a new path. `TaskQueue` offers internal owner-scoped enqueue, ready, claim, retry, timeout recovery and cancel state. It stores priority, a bounded attempt limit and backoff, optional deadline, availability time, and immutable lease records. A claim increments attempts; leases expire at the earlier of their timeout and deadline. Recovery is explicit, never automatic. A failed attempt requeues after backoff, or becomes exhausted when the attempt limit is reached or the deadline prevents another attempt. Queued items past their deadline are excluded from ready results and may be cancelled, but are not automatically changed. Recovery and retries require the current lease ID, preventing stale IDs from changing a later lease. An identical claim retry returns its original lease ID even when inactive; check `get_lease` and do not assume a retried result is current. Same state mutations atomically record fixed audit events and shared per-owner idempotency keys. Ordering is priority descending, availability time, then ID, not strict FIFO. This is scheduling state only: it does not execute work, validate output, implement approval, or establish completion. It relies on a trustworthy wall clock and trusted local caller; leases alone cannot fence external effects.

### Experimental local task review

The explicit, checked-backup-first v7-to-v8 migration adds a separate `task_workflows` table. `TaskWorkflows` uses live-session ownership and atomic audit/idempotency for `planned -> in_progress -> pending_review -> completed`; review may instead reject to `in_progress`, and pre-completion states can be cancelled. Submitted output must be nonempty, bounded UTF-8 text without most control characters; only its SHA-256 digest and byte length are stored. Review requires literal `confirmed=True`, an explicit boolean decision and output whose digest and length match the submission. An identical operation-key retry returns its original result, even after later changes. This is local state only: no worker runs, and no queue entry is linked or completed. Validation is syntactic, not business or factual validation; confirmation does not establish human identity or permission to deliver externally. Hashes may reveal guessable content. This internal disposable prototype and v8 are unverified on Windows.
